# pi-memory-md 记忆隔离与污染分析

> 结论：**读取方向是隔离的，不会自动跨项目污染；但写入没有沙箱，有 4 个真实的坑。**
> 全部结论均用 `jiti` 加载插件真实源码 + 模拟 pi 对象**实测确认**，非推测。

## 一、隔离做对的部分

| 机制 | 行为 | 源码 |
|---|---|---|
| 上下文注入 | 只注入 **2 个 scope**：`global/` + **当前项目分区**；其他项目分区完全不出现 | `memory-core.ts` `buildMemoryContextAsync()` |
| 分区判定 | `localPath / basename(git 仓库根目录)`，按项目天然分开 | `getMemoryDir()` |
| `memory_search` | `scope` 默认 `project`，只搜当前分区 | `tools.ts:412` |
| `scope: "all"` | **不是**「所有分区」，而是 `project + global`；其他项目永远搜不到 | `tools.ts:425-432` |

比 `pi-memory-agent` 省心：**不用手动切记忆体，自动按项目隔离**。

## 二、4 个污染风险点

### 坑 1：同名目录 = 同一个分区（唯一的「自动污染」）— 已实测
`getMemoryDir()` 只用 `path.basename()`，**丢掉完整路径**：

```
D:/工作学习/git的测试使用      →  memory-md\git的测试使用
E:/别的盘/备份/git的测试使用    →  memory-md\git的测试使用   ← 同一个分区！
```

`D:/work/api` 与 `E:/backup/api` 会共用记忆。**配置层面无解**，只能避免同名目录。

### 坑 2：`global/` 注入到每一个项目 — 设计如此
放进 global 的内容在**任何项目**都会出现在上下文里。这是它的用途，也是最大污染源：
**agent 一旦把项目专属信息误写进 global，就污染了全部项目。**
→ 纪律：只有真正跨项目通用的事实才进 global。

### 坑 3：`core/` 之外的文件 = 白写 — 已实测
项目分区的**注入根和搜索根都写死为 `<分区>/core/`**：

| 探针位置 | 被注入 | 被搜索到 |
|---|---|---|
| `core/project/` 内 | ✔ | ✔ (count=1) |
| `docs/`（core 之外） | ✘ | ✘ |

但 `memory_check` **照样统计进去**（报了 3 个文件）→ **数字会骗人**。
→ 纪律：项目记忆一律放 `<分区>/core/` 下（`core/project/` 放项目记忆）。

### 坑 4：`memory_search(scope="global")` 在平铺 global 结构下直接失效 — 已实测

```
scope=project  →  count=1
scope=global   →  "Memory directory not found for scope: global"   ← 失效
scope=all      →  count=1   ← 静默等于 project，global 被跳过！
```

原因：搜索根写死为 `<memoryDir>/core`（`tools.ts:432`），而初始化脚本建的 `global/` 是**平铺的、没有 `core/` 子目录**。
**注入用整个 global 目录（读得到），搜索只扫 `global/core`（读不到）—— 两边口径不一致。**

**修复方案（二选一）**
- **A. 结构法（推荐）**：把 `global/*.md` 移到 `global/core/*.md`。零代码改动；注入照样读得到（递归扫整个 global）；搜索恢复正常。符合 skill 自己的规则「always-needed context under `core/`」。**插件更新后依然有效。**
- **B. 改代码**：让 global 的搜索根用 `memoryDir` 而非 `coreDir`。一处一行，但更新插件后补丁会丢。

## 三、其他实测发现

- **实际只注册 3 个工具**：`memory_sync`、`memory_search`、`memory_check`。
  `memory_read` / `memory_write` / `memory_list` / `memory_init` 在 0.1.38 源码里**全是注释状态**（`tools.ts:216/268/325/606`）。
  → 后果：**写记忆没有沙箱**，靠 native `write`/`edit` 直接写文件，写错分区不会报错，全靠遵守 `memory-write` skill 的路径规范。这也是「注入的是索引而非正文」的配套设计——需要细节时 agent 自己用 read 读文件。
- `loadSettings()` 会 `deepMerge(全局 settings, 项目 .pi/settings.json)`，并把 `memoryDir.repoUrl/localPath` **同时提升到顶层**；`memoryDir.globalMemory` 只从嵌套结构读。
- 判断「已初始化」看的是 `<分区>/core/user/` 是否存在（`isMemoryInitialized`）。
