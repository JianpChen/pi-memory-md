# 软件测试学习

## 测试思维（最重要的三句话）
1. **测试是质量保障，不是找茬** —— 目标是帮团队降低风险，不是证明别人写错了
2. **测试无法穷尽** —— 输入空间无限，必须按**风险优先级**取舍
3. **测试越早介入越好** —— 需求阶段就能发现的问题，代价远低于上线后

## 测试类型
| 类型 | 关注点 |
|---|---|
| 功能测试 | 是否满足需求 |
| 边界值测试 | 极值、临界、越界 |
| 异常测试 | 错误输入、异常路径 |
| 兼容性测试 | 不同系统 / 浏览器 / 设备 |
| 性能测试 | 响应时间、吞吐、资源占用 |
| 回归测试 | 改动后旧功能是否被破坏 |

## 核心设计方法
- **等价类划分**：把输入域切成若干等价类（有效类 / 无效类），每类取一个代表值——用最少的用例覆盖最大的输入空间
- **边界值分析**：错误最常出现在边界上（`min-1`、`min`、`min+1`、`max-1`、`max`、`max+1`），单独设计用例
- 两者通常**配合使用**：先划分等价类，再对每类的边界加测

## bug 报告要素
一份合格的 bug 报告要能让开发**不追问就复现**：
- 标题（一句话说清现象）
- 环境（系统 / 版本 / 配置）
- 复现步骤（精确、可执行、编号）
- 实际结果 vs **预期结果**
- 严重程度 / 优先级
- 附件（截图、日志、录屏）

## 学习路径（当时规划的）
测试思维 → 测试类型 → 等价类划分 / 边界值分析 → 常见坑 → bug 报告 → 实战

## 常见坑
- 只测「正常路径」，不测异常和边界
- 用例没有预期结果，无法判断通过与否
- bug 报告只写「不好用」，无法复现
- 只做一次性测试，没有回归
